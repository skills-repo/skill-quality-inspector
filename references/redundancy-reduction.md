# 冗余识别与去重原则（redundancy-reduction）

> 组织扩张到 30+ 仓库后，功能重叠几乎必然发生。本篇负责把重叠"暴露出来"，但去重必须守住"只增不减"铁律。

## 一、重叠判据（三层）

| 判据 | 方法 | 误报风险 |
|------|------|----------|
| **重名** | 跨仓库扫描 `skills/<name>/SKILL.md` 的 `name` 字段，全局去重 | 低（同名即冲突） |
| **近重描述** | 对 `description` 做 token 集合，算 Jaccard 重叠，>0.6 标记候选 | 中（换说法的软重叠会漏） |
| **关键词打架** | 比对各仓库根 SKILL.md 路由表的 grep 关键词，发现跨仓触发词高度重合 | 中（合理重叠不算冗余） |

## 二、判定：真重叠 vs 误报

命中候选后，按以下规则过滤：
- 同名但 `category` 不同且面向不同用户场景 → **不一定冗余**（如不同领域的同名工具技能）。
- 描述近重但能力清单差异明显 → **软重叠**，标 `review_needed`，不强制合并。
- 关键词打架但解决的"任务动词"不同 → **合理分工**，不处理。
- 真正冗余的信号：**能力清单高度同质 + 触发场景重叠 + 用户二选一困惑**。

## 三、去重流程（只增不减）

```
1. redundancy_scan.py --org <root> --json → 重名/近重/关键词重叠三类候选
2. 人工过滤误报（见上）
3. 对真重叠三选一处置：
   a. 合并：新建聚合子技能，把两处能力收口（新增，不动旧路径）
   b. 下线：旧路径标 deprecated: true（保留目录，frontmatter 加 deprecated）
   c. 保留：确认分工合理，跳过并备注理由
4. 合规兜底：任何建议都要过 skills-lock.json 校验——
   被锁定的 source 路径不得改名/删除，否则下游安装直接失效
5. 同步 registry/repos.json（skills 计数、updated）
```

## 四、"只增不减"铁律

- 已有 `skills/<name>/` 目录**不得删除或重命名**——`skills-lock.json` 锁定了下游引用路径。
- 需要淘汰 → 标 `deprecated: true`，让 Agent 在路由时跳过，但磁盘仍在。
- 合并出的新技能是"新增"，不是"替换"，旧路径保留到下游自然迁移。

## 五、典型坑

- **软重叠漏报**：Jaccard 抓不到"换个说法说同一件事"，必须人工终审近重候选。
- **误删锁路径**：直接删目录会让已安装用户 `npx skills add` 失效，回滚成本高。
- **过度合并**：把"合理分工"当冗余合并，反而制造单点巨技能，违背渐进式加载。
